# 提示词工程之前，先做问题定义：把 AI 任务写成一份可验证的接口契约

生成式 AI 进入研发和知识工作以后，很多失败会被归因成“提示词写得不够好”。于是团队不断加角色、步骤、示例和格式约束，Prompt 越来越长，输出却未必更可靠。

问题往往不在句式，而在任务接口没有定义清楚。

“帮我生成一份最好的分析报告”看起来像请求，实际上缺少调用者、输入、目标、范围、风险和验收条件。模型只能用训练中常见的模式补全这些空白。生成结果可能结构完整，却无法回答三个工程问题：它用了什么事实？哪些条件是猜的？怎样判定可以被采用？

本文使用一张“背景—目标—限制—检查”四格卡，把 AI 请求从自然语言愿望改写成可观测、可回退的任务契约。

## 一、Prompt 不是问题定义

先看一个常见请求：

```text
请帮我写一份全面、专业、有深度的植物观察报告。
```

“全面、专业、有深度”只描述了期待的感觉，没有定义系统行为。至少还有这些未知：

- 报告给谁使用？
- 已经有哪些观察数据？
- 哪些内容允许从公开资料补充？
- 观察持续多长时间？
- 哪些结论必须由原始记录支持？
- 没有数据时应该怎样表达？
- 最后由谁检查并承担发布责任？

如果调用方不处理这些未知，模型会给它们填入隐式默认值。真正的风险不是“回答得不够漂亮”，而是默认值没有经过授权，却混进了看似确定的结果。

可以把这类失败抽象成：

```text
underspecified request
  -> model fills implicit defaults
  -> fluent candidate artifact
  -> no explicit acceptance criteria
  -> candidate is mistaken for accepted result
```

Prompt 技巧可以改善表达，但不能替代接口契约。

## 二、四格卡对应什么工程对象

### 1. 背景：调用上下文与已授权输入

背景回答“谁在什么情境下使用结果，以及系统可以拿到什么”。

它可以映射为：

- caller / user role
- known state
- authorized inputs
- source inventory
- assumptions already confirmed

需要特别区分“完成任务必需的上下文”和“方便但无必要的个人信息”。姓名、学校、精确位置、账号、私人聊天等，不应因为模型可能用得上就默认进入输入。

### 2. 目标：期望产物与实际用途

目标不是“给出一个好答案”，而是：

- 产物是什么类型？
- 谁准备怎样使用？
- 它支持哪个决定或下一步？
- 哪些部分只能作为候选？

同一组资料，可以生成摘要、对比表、待核验断言列表或行动候选。产物类型不同，允许模型承担的工作也不同。

### 3. 限制：输入、处理与输出约束

限制至少包含四类：

```text
scope constraints
source constraints
format constraints
safety/privacy constraints
```

例如：“只能使用提供的七天观察记录；没有记录的内容写 unknown；不得推断具体家庭或个人情况；输出为三列表格。”

限制的价值不是让 Prompt 更长，而是减少未经确认的自由度。

### 4. 检查：验收条件与责任人

很多请求写了格式，没有写验收。

检查应该说明：

- 哪些事实要回到原文？
- 哪些字段必须非空？
- 哪些不确定项允许保留？
- 什么情况应该拒绝、回退或请求补充？
- 谁执行检查？
- 谁接受或拒绝候选结果？

没有 validator 和 accountable owner 的 AI 节点，只是在生产一个更像成品的候选。

## 三、把隐藏默认值变成澄清问题

任务定义不完整时，常见做法是直接让模型生成第一版，再靠多轮修改逼近目标。这会把错误假设带进后续上下文。

更稳妥的做法是先运行输入校验：

```text
先不要执行任务。
请检查背景、目标、限制和验收条件还缺什么；
最多提出 5 个澄清问题；
不要猜测未说明的信息；
不要询问与任务无关的身份信息。
```

这一步相当于把 `implicit defaults` 转成 `validation errors` 或 `clarification requests`。

但模型提出的问题仍只是候选。调用方需要决定：

- 这个问题是否真的影响结果？
- 回答它是否需要不必要的数据？
- 是否可以用虚构、去标识化或更小范围的条件代替？
- 如果不回答，系统是否应该拒绝继续？

## 四、一个任务契约示例

原始请求：

```text
帮我写一份植物观察报告。
```

改写后的任务契约：

```yaml
context:
  user: 一名需要整理个人观察的学生
  available_data:
    - 七天豆苗高度记录
    - 两张不含人物的植物照片
goal:
  artifact: 80 字观察摘要候选
  use: 由学生继续修改和解释
constraints:
  sources: 只使用七天原始记录
  unknowns: 未记录内容写 unknown
  privacy: 不输入姓名、学校、位置或账号
  ownership: 最终解释由学生完成
acceptance:
  - 每个变化都能回到原始记录
  - 不补写未观察到的事实
  - 明确列出至少一个未知
  - 关闭 AI 后，学生能说明最终结论
```

在这个契约里，模型的输出被明确为 `candidate artifact`，而不是 `accepted result`。验收仍由人执行。

## 五、从一次调用扩展为可观测流程

一个最小流程可以写成：

```text
task definition
  -> input validation
  -> clarification
  -> authorized input
  -> AI candidate
  -> evidence check
  -> accepted / rejected / uncertain
  -> accountable human decision
```

这里有两个常被忽略的状态：

### rejected

候选没有满足资料、隐私或验收条件，应被明确拒绝，而不是继续润色。

### uncertain

资料不足、来源冲突或条件不适用时，系统应该允许停在“不确定”。如果流程只能输出成功或失败，模型就容易用生成内容填满未知。

## 六、对 Agent 和工作流系统的启示

当单次对话扩展成 Agent、RAG 或多节点工作流，四格卡仍然适用，只是对象变得更具体：

| 四格 | 工作流映射 |
|---|---|
| 背景 | 状态、身份、可用工具、已授权数据 |
| 目标 | 目标状态、产物 schema、下游消费者 |
| 限制 | 工具白名单、数据边界、预算、超时、禁止动作 |
| 检查 | validator、evidence、rollback、human gate、owner |

如果只给 Agent 一个宏大目标，却没有限制和检查，它会把“自主”理解成补全更多默认值。真正可控的自主性，来自明确授权范围、可见中间产物和可执行停止条件。

## 七、给家庭学习任务的最小版本

这套方法也可以讲给 8—14 岁孩子，但不需要引入接口术语。只问四句话：

1. 我已经知道什么？
2. 我真正要得到什么？
3. 哪些条件不能忽略？
4. 我怎样知道做完了？

然后让 AI 先提澄清问题，不直接交成品。孩子确认条件后再继续，并在关闭 AI 后解释自己的结论。

这比背一个“万能提示词”慢一点，却保留了更关键的东西：任务方向、证据检查和最终责任仍然在人手里。

## 结语

Prompt 工程不是没有价值。角色、上下文、示例和输出格式都能改善模型行为。但它们应该建立在问题定义之上。

在写下一条复杂 Prompt 前，先检查：背景、目标、限制、检查是否真的明确；模型是在执行一个已经定义的任务，还是在替调用方猜任务是什么？
