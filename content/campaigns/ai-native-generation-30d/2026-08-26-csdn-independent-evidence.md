# 两个网页不等于交叉验证：给 AI 输出建立断言、证据与独立来源图

生成式 AI 回答带上引用以后，很容易给人一种“已经核验”的感觉。再找到第二个网页，似乎就完成了交叉验证。

但两个 URL 可能都改写自同一篇新闻、引用同一份报告，甚至第二个网页只是第一个网页的转载。页面数量增加了，证据路径没有增加。

真正的验证对象不是整段回答，也不是链接数量，而是：一条具体断言、原文真正支持的范围、反例条件，以及来源之间是否独立。

本文给出一套适用于 Agent、RAG 和普通 AI 对话的最小验证模型。

## 一、先把流畅回答拆成最小断言

下面这句话很难直接验证：

```text
研究表明，这种方法能显著提高儿童的学习能力，因此适合所有家庭长期使用。
```

它至少包含四个不同断言：

1. 存在一项可以定位的研究；
2. 研究对象包含儿童；
3. 观察到的指标可以被称为“学习能力”；
4. 研究结果可以外推到所有家庭和长期使用。

前两项可能是事实存在性问题，第三项涉及指标解释，第四项涉及外推。一个来源即使支持“短期任务得分变化”，也不能自动支持“长期学习能力提升”。

因此验证的第一步是建立 `claim unit`：

```json
{
  "claim": "在研究样本和实验周期内，方法 A 提高了指标 B",
  "claim_type": "empirical",
  "scope": {
    "population": "研究样本",
    "duration": "实验周期",
    "metric": "指标 B"
  },
  "impact": "medium"
}
```

断言越具体，证据范围越容易比较。

## 二、来源卡不只记录 URL

最小来源卡可以包含：

```yaml
source:
  publisher: 发布机构或作者
  title: 原文标题
  published_at: 日期
  source_type: primary | secondary | commentary
  location: 原文页码、段落或表格
  supports: 支持到哪一个范围
  conditions: 样本、时间、地域、指标和方法限制
  conflicts: 与断言不一致的部分
```

仅记录 URL 有三个问题：

1. 页面可能更新，定位不到当时支持句；
2. 标题可能比正文结论更强；
3. 二手文章可能省略原始研究条件。

验证时至少要能回答：原文在哪里？支持到什么范围？哪些部分没有支持？

## 三、把“支持”拆成四种状态

证据与断言不是简单的 true / false 关系。更实用的状态是：

```text
supported
partially_supported
contradicted
not_found
```

### supported

原文直接支持当前范围的断言，适用条件与当前问题一致。

### partially_supported

只支持其中一部分，或研究条件比断言更窄。此时应该缩小断言，而不是继续找一句更像背书的话。

### contradicted

原文结论、数据或条件与断言冲突。

### not_found

页面存在，但找不到支持位置；或者引用链无法回到可检查的原始材料。

“not found”不是“证明它错了”，但足以阻止系统把该来源当作已验证证据。

## 四、反例不是抬杠，而是范围测试

验证不仅问“有没有支持”，还要问“在什么条件下不成立”。

例如，一个任务拆解方法在结构清晰、资料充足的场景中有效，不代表在紧急、高风险或隐私敏感场景里仍适用。

可以给模型一个受限的反例任务：

```text
不要替我否定结论。
请列出 3 个会使当前断言不成立或需要缩小范围的条件，
并标明这些条件来自原文、逻辑边界还是尚待验证的假设。
```

反例输出仍需要核验。它的作用是暴露断言范围，而不是让模型用另一段生成内容推翻自己。

## 五、两个来源是否真的独立

可以把来源关系画成图：

```text
claim C
 ├─ article A ── cites ── report R
 └─ article B ── cites ── report R
```

A 和 B 是两个网页，但只有一条原始证据路径 R。

更接近独立交叉检查的结构是：

```text
claim C
 ├─ primary source R1: method/data path 1
 └─ primary source R2: method/data path 2
```

判断独立性可以检查：

- 作者或机构是否不同；
- 原始数据是否不同；
- 研究方法是否独立；
- 是否互相转载或引用；
- 是否都回到同一份新闻稿、报告或数据库；
- 时间和样本是否只是重复发布。

这里的“独立”也不是绝对值。可以记录为：

```text
independent
partially_independent
same_origin
unknown
```

找不到引用链时，不要默认独立，标成 unknown。

## 六、一个验证状态机

将断言、来源、反例和独立性合在一起，可以得到一个简单状态机：

```text
unverified
  -> source located
  -> support checked
  -> conditions checked
  -> counterexample checked
  -> independence checked
  -> accepted / narrowed / rejected / uncertain
```

### accepted

当前范围有来源支持，关键条件匹配，且错误后果可接受。

### narrowed

证据只支持更小范围，系统修改断言后接受。

### rejected

原文冲突、来源伪造、条件明显不适用，或风险超过授权范围。

### uncertain

来源不足、引用链不清、独立性未知或证据冲突。流程允许停止，不继续生成一个确定答案。

## 七、在 RAG 和 Agent 中怎样落地

### 1. 检索结果与证据对象分离

Retriever 返回的是候选文档，不是 evidence。只有定位到支持位置、检查条件后，才能升级为证据对象。

### 2. 引用数量不作为唯一指标

“回答包含 5 个引用”无法证明事实更可靠。更有用的指标包括：

- claim coverage：关键断言有多少被检查；
- entailment scope：来源支持的范围是否与断言一致；
- source independence：关键断言是否存在独立路径；
- uncertainty calibration：证据不足时是否降低确定性；
- high-impact escalation：高影响结论是否触发人工门禁。

### 3. 保留验证日志，但避免收集无关数据

可以记录断言、来源位置、验证状态和责任人，不需要顺手保存用户完整对话、身份信息或原始私人材料。

### 4. 将 human-in-the-loop 放在接受节点

人不是在最后“看一眼”，而是决定候选断言是否进入 accepted state。高影响建议、隐私材料和对外发布，需要更明确的人工门禁。

## 八、给孩子的三层版本

同一套结构可以压缩成三个动作：

1. **找原文**：链接能不能打开，原文在哪里？
2. **找反例**：什么条件下这句话不成立？
3. **找独立来源**：第二个网页是不是仍引用同一份材料？

评论区不需要上传完整聊天或作品，只记录：

```text
断言类型｜原文支持范围｜一个反例条件｜第二来源是否独立｜最终状态
```

资料不足时写“目前不能确认”，也是有效完成。

## 结语

验证不是在生成回答后加几个链接，而是重新定义输出的生命周期：模型先产生候选断言，证据检查决定范围，独立来源提高可信度，人决定接受、缩小、拒绝或保留未知。

两个网页只有在证据路径真正独立时，才可能构成交叉验证。否则只是同一个结论被复制了两次。
