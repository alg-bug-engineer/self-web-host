# 技术内容方向

## 目标与读者

以「芝士AI吃鱼」建立 AI 时代的大模型专家个人品牌。面向希望理解原理、做出可靠 AI 应用的开发者，积累可以被检查、复现和引用的技术内容。保持「把 AI 天书，讲成人话」的表达，同时把条件、证据与限制讲清楚。

## 每篇文章的最低要求

- 解决一个具体问题；先检查既有文章，避免换标题重复发布
- 重要事实优先引用原始论文、官方文档或项目源码，并标明核对日期、版本和适用条件
- 区分亲自运行的结果、来源报告的结果、合成样例和待验证假设；不虚构作者经历、测试、数据或效果提升
- 尽量提供能独立使用的代码、测试、故障案例或分析图；工具安装本身不能替代技术解释
- 指标写清定义、分母、样本和边界；公开资料不得包含私有用户数据或凭证
- 公开文章本身应完整解决承诺的问题。知识星球与公众号承接相关讨论，沿用已核验入口，不虚构会员资源、服务或效果承诺

## RAG 评测实战

1. 已编写：检索命中了，为什么答案还是错的？以手工合成数据和可运行计分器说明证据召回、事实覆盖、支持度与拒答
2. 候选：切块与版本管理。固定原始文档和问题集，比较切块如何影响证据定位，处理跨切块 ID 映射
3. 候选：混合检索与重排。用固定数据和预算运行对照，报告逐题变化、延迟与成本
4. 候选：从评测到发布。标注质量、评审模型校准、权限边界与线上失败回归

后续题目须先核对资料与可运行条件，不因日历安排而发布缺少实质内容的文章。Agent、上下文工程和模型机制可作为后续系列，以具体技术问题及验证条件决定顺序。

## 发布检查

先验证样例与边界测试，再执行仓库 CI 中的检查、lint、生产构建和桌面/移动端 UI 回归。检查正文、可下载文件、站内链接、canonical、sitemap、RSS 与 Markdown 输出。使用现有 PR/CI 和部署流程；上线后核对精确提交与公开页面。

保留既有未发布草稿的状态，不自动公开儿童 AI 活动稿，也不绕过已有会员预览、来源核验或部署锁。内容发布与增长归因分开，搜索曝光变化不能自动证明某个改动有效。
