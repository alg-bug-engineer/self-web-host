# 内容方向与更新节奏

## 目标与读者

以「芝士AI吃鱼」建立 AI 时代的大模型专家个人品牌。面向希望理解原理、做出可靠 AI 应用的开发者，积累可以被检查、复现和引用的技术内容。保持「把 AI 天书，讲成人话」的表达，同时把条件、证据与限制讲清楚。

## 每篇文章的最低要求

- 解决一个具体问题；先检查既有文章，避免换标题重复发布
- 重要事实优先引用原始论文、官方文档或项目源码，并标明核对日期、版本和适用条件
- 区分亲自运行的结果、来源报告的结果、合成样例和待验证假设；不虚构作者经历、测试、数据或效果提升
- 尽量提供能独立使用的代码、测试、故障案例或分析图；工具安装本身不能替代技术解释
- 指标写清定义、分母、样本和边界；公开资料不得包含私有用户数据或凭证
- 公开文章本身应完整解决承诺的问题。知识星球与公众号承接相关讨论，沿用已核验入口，不虚构会员资源、服务或效果承诺

## 每日双线目标

按 Asia/Shanghai 自然日推进两条独立内容线：每天 1 篇 AI 锐评 + 1 篇成系列技术长文。长文围绕连续的技术问题、可核验资料与可运行实验展开，不用普通常青文章或第二篇锐评抵数。缺少新事实、证据、实验或质量不足时停止，记录缺项和待完成验证，不为数量凑稿。

发布判据取已 fetch 的 `origin/main` 中 frontmatter 的 `date`、`published`、`postType` 和系列元数据，不按文件名中的日期，也不把本地文件、分支候选稿或 `published: false` 草稿视作已发布。时间戳换算为上海日期；仅有日期时按该自然日判断。旧文章缺省 `postType` 为 `article`、缺省 `published` 为 `true`，与站点模型一致。

当前技术系列注册规则为 `category: tech`（默认 tech），并匹配以下任一组合：`topicCluster: rag-engineering` + `topicId: rag-evaluation-<数字>`，或 `topicCluster: agent-reliability` + `topicId: agent-reliability-<数字>`；标题、标签、普通 `engineering` 主题簇都不能替代系列标记。新增系列须先审查系列规划并扩展注册规则。此规则识别出版线，不代替正文质量、实验或长文完整度审核。

## AI锐评：日更观点，与技术长文分开

- 栏目入口 `/commentary`；正文仍使用 `/blog/<slug>`，只有一个 canonical。首页和导航有独立入口，`/blog` 的「AI锐评」筛选按 `postType` 分类，不依赖标题或模糊标签
- 锐评 frontmatter 使用 `postType: commentary`，`commentaryTopic: events | products | industry`（热门事件 / 产品观察 / 行业变化）。保留既有 `category: tech | life`、标签与 `published` / `access` 规则；技术长文默认 `postType: article`
- 每天检查新事件，目标每天一篇值得读的观点，同时推进一篇技术系列长文。没有增量事实或明确判断时停止该线发布，不能为了凑日更重复改写旧文；技术系列缺少证据或实验验证时也停止，明确标记当天缺项
- 从一个具体事件或产品变化切入：发生了什么、谁受到影响、作者为什么在意、自己的判断是什么。情绪要来自实际得失，避免空泛激昂、发布会复述和统一套用“三点建议/结语”模板
- 用原创且连贯的场景或意象推进：有趣的冲突开场，转入真实事件，再讲技术原因，结尾回扣前面的场景。类比只负责帮人理解，不能冒充原理或亲历；幽默和情绪点到为止，不模仿其他作者的标志性句式
- 本栏图解采用清晰的矢量信息图：白底、蓝色标题、简短灰色副标题，浅蓝/青绿/浅红卡片配细边框、箭头或阶梯，黄色结论条；用原创信息结构讲清问题，不照抄参考文字。移动端提供单独的纵向版本，正文标签不靠缩小整张横图来适配
- 需要配图时，让插图承担叙事或解释作用，并遵循本篇已确认的视觉方向；不拿泛用配图凑数量，也不把装饰图伪装成实验结果。具体参考不可见时先补齐参考，不自称已经匹配了画风
- 重要事实贴原始链接并说明核对日期；把厂商自述、已确认事实、作者推断分开。不得虚构亲测经历、数据、引语、现场感或身份；不靠无证据指控制造尖锐
- 标题可以有态度，但要能被正文支撑；写清适用条件和反例。内容以观点推进为准，不强塞代码、配图和长文四段式
- 首发前对照最近锐评检查重复；新证据出现时修正原文并说明改动。锐评进入全站 RSS，同时提供仅含已发布锐评的 `/commentary/feed.xml`
- 沿用一个现有每日发布流程，不新增并行 cron / Actions / launchd 定时任务。保留 PR、CI、部署核验；外部平台发布仍按对应授权与发布门槛处理

## RAG 评测实战

1. 已编写：检索命中了，为什么答案还是错的？以手工合成数据和可运行计分器说明证据召回、事实覆盖、支持度与拒答
2. 已编写：《RAG 评测实战（二）：切块一改，召回率为什么就失真了？》。slug：`rag-evaluation-02-chunking-evidence-mapping`。固定原始文档和问题集，比较切块如何影响证据定位，处理跨切块 ID 映射；发布仍须完成实验、质量与上线核验
3. 已编写：《RAG 评测实战（三）：两路词法检索，怎样测 RRF 与重排？》。slug：`rag-evaluation-03-rrf-candidate-reranking`。固定合成数据、BM25 与显式查询扩展两路，运行 RRF、规则重排、候选深度与最终预算对照；报告逐题变化与操作计数，不冒充向量/神经重排 benchmark 或生产延迟、费用。发布仍须实验、质量与上线核验
4. 已编写：《RAG 评测实战（四）：平均分涨了，就能上线吗？》。slug：`rag-evaluation-04-release-gates`。以合成记录演示评审阈值选择、同题配对、关键退化与权限线索的离线发布门禁；不冒充真人标注、LLM 评审实测、真实 ACL 或独立留出验证。发布仍须实验、质量与上线核验
5. 已编写：《RAG 评测实战（五）：引用都挂上了，证据真的撑住了吗？》。slug：`rag-evaluation-05-citation-audit`。固定 ALCE 官方历史输出与评审档案，重算问题/句子/引用分母、截断范围和人工/自动分歧；不复制上游文本，不冒充当下模型调用、NLI 重跑、命题级新标注或真实拒答验证。精确服务端模型快照未提供，仅重现字节与统计。发布仍须实验、质量与上线核验
6. 候选：新生成输出的命题级支持与拒答审计。待具备可运行模型、可固定版本的真实输出和证据、可审查细粒度标签后推进；区分当前模型实测与第五篇历史档案重放，不用合成模板字符串填补缺失条件

后续题目须先核对资料与可运行条件，不因日历安排而发布缺少实质内容的文章。Agent、上下文工程和模型机制可作为后续系列，以具体技术问题及验证条件决定顺序。

## Agent 可靠执行实战

1. 本期：工具已执行，回执丢了怎么办？以 Python 标准库、SQLite 与真实子进程退出实验，区分发送端持久化、接收端事务去重和外部副作用；操作内容为合成工单，不调用模型或真实业务服务
2. 候选：多工作进程的租约、过期与 fencing。需用可复现交错证明旧工作进程不能覆盖新结果，不用一个锁变量冒充分布式保障
3. 候选：不可幂等工具的 unknown 状态与人工对账。需明确查询能力、补偿与授权边界，不能把重试当成恢复

本系列注册为 `topicCluster: agent-reliability`、`topicId: agent-reliability-<数字>`。RAG 第六篇的真实生成与细粒度审计条件保持待满足，不用本系列实验冒充 RAG 输出评测。候选题须先具备实质证据再写作。

## 发布检查

先验证样例与边界测试，再执行仓库 CI 中的检查、lint、生产构建和桌面/移动端 UI 回归。检查正文、可下载文件、站内链接、canonical、sitemap、RSS 与 Markdown 输出。使用现有 PR/CI 和部署流程；上线后核对精确提交与公开页面。

保留既有未发布草稿的状态，不自动公开儿童 AI 活动稿，也不绕过已有会员预览、来源核验或部署锁。内容发布与增长归因分开，搜索曝光变化不能自动证明某个改动有效。
